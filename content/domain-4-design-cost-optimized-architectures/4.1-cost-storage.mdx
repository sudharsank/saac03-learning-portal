# 4.1 — Cost-Optimized Storage Solutions

<Concept>
## What Is It?

AWS offers a spectrum of storage services — S3, EBS, EFS, Glacier — each with multiple pricing tiers designed for different access patterns and durability requirements. Cost-optimized storage means matching the **retrieval frequency** of your data to the **cheapest storage class that still meets your SLA**, then automating transitions over time with lifecycle policies.

S3 alone has seven storage classes ranging from $0.023/GB/month (Standard) down to $0.00099/GB/month (Deep Archive), a 23x price difference. Choosing the wrong class for cold data is one of the most common sources of avoidable AWS spend. Similarly, EBS defaults to gp2 for many workloads even though gp3 delivers the same or better performance at 20% lower cost.

Effective storage cost management requires three skills: selecting the right storage class at object creation, configuring lifecycle rules to transition or expire objects automatically, and right-sizing block and file storage volumes. Together, these can reduce storage bills by 50–80% on data-heavy workloads.

## Key Components

- **S3 Storage Classes** — Standard, Intelligent-Tiering, Standard-IA, One Zone-IA, Glacier Instant Retrieval, Glacier Flexible Retrieval, Glacier Deep Archive
- **S3 Lifecycle Policies** — Transition rules (move to cheaper class), expiration rules (delete objects), multipart upload cleanup
- **S3 Intelligent-Tiering** — Automatic tiering with small per-object monitoring fee; no retrieval charges
- **EBS Volume Types** — gp3 (general purpose), io2 (provisioned IOPS), sc1/st1 (throughput-optimized HDD)
- **EBS Snapshot Lifecycle Manager (DLM)** — Automated snapshot creation and deletion policies
- **EFS Storage Classes** — Standard + Infrequent Access (IA) tiers with lifecycle management
- **S3 Requester Pays** — Transfers cost billed to the requester, not the bucket owner
</Concept>

<DeepDive>
## How It Works

### S3 Storage Class Pricing Tiers

S3 storage classes form a cost-vs-availability spectrum. Understanding the trade-offs is the foundation of cost-optimized storage design:

| Storage Class | $/GB/month | Min Duration | Retrieval Fee | Use Case |
|---|---|---|---|---|
| Standard | $0.023 | None | None | Frequently accessed data |
| Intelligent-Tiering | $0.023 (active) | None | None | Unknown access patterns |
| Standard-IA | $0.0125 | 30 days | Per GB | Infrequent but fast retrieval |
| One Zone-IA | $0.01 | 30 days | Per GB | Non-critical, re-creatable |
| Glacier Instant | $0.004 | 90 days | Per GB | Archives needing ms retrieval |
| Glacier Flexible | $0.0036 | 90 days | Per GB + request | Archives with hours retrieval |
| Deep Archive | $0.00099 | 180 days | Per GB + request | Long-term compliance archives |

**Minimum storage duration** means if you store an object for less than the minimum and then delete or transition it, you are still charged for the full minimum period. This is a significant cost trap for small or short-lived objects.

### S3 Intelligent-Tiering

Intelligent-Tiering monitors object-level access and automatically moves objects between an **Frequent Access** tier (Standard pricing) and an **Infrequent Access** tier (Standard-IA pricing) after 30 days of no access. For objects not accessed for 90 days, it can optionally move them to the **Archive Instant Access** tier.

The cost model:
- **Monitoring fee**: $0.0025 per 1,000 objects monitored per month
- **No retrieval charges**: Unlike Standard-IA, there is no per-GB retrieval fee regardless of which internal tier the object is in
- **Break-even**: If 40%+ of objects in a Standard-IA bucket go unaccessed for 30 days, Intelligent-Tiering pays off

Intelligent-Tiering is best for buckets with mixed or unpredictable access patterns — for example, user-generated content where some files are accessed constantly and others are never touched again.

### S3 Lifecycle Policies

Lifecycle rules automate cost management without application changes. A lifecycle configuration is a set of rules attached to a bucket, each with a filter (prefix, tags, object size) and one or more actions:

**Transition actions** move objects to a cheaper storage class after a specified number of days since object creation. Transition hierarchy (you can only go down, never up via lifecycle):

```
Standard → Standard-IA (min 30 days) → Glacier Instant (min 90 days) → Glacier Flexible → Deep Archive
```

**Expiration actions** delete objects automatically. Useful for:
- Log files (expire after 90 days)
- Temporary upload staging directories
- Old application versions

**Multipart upload cleanup**: Large files uploaded in parts leave behind incomplete multipart uploads if the upload fails. These consume storage without creating usable objects. A lifecycle rule with `AbortIncompleteMultipartUpload` after 7 days prevents this silent cost accumulation.

**Example lifecycle strategy for logs**:
```
Day 0: Write to Standard
Day 30: Transition to Standard-IA
Day 90: Transition to Glacier Flexible Retrieval
Day 365: Expire (delete)
```

### EBS Cost Optimization

EBS volumes are billed per GB-month provisioned (regardless of use) plus per IOPS provisioned (for io1/io2). Key cost levers:

**gp3 vs gp2**:
- gp2: IOPS tied to volume size (3 IOPS/GB, max 16,000 IOPS at 5,333 GB)
- gp3: Baseline 3,000 IOPS and 125 MB/s included free, independently scalable up to 16,000 IOPS and 1,000 MB/s
- gp3 is $0.08/GB/month vs gp2 at $0.10/GB/month — 20% cheaper at the same size
- For a 1TB volume needing 3,000 IOPS: gp2 = $100/month, gp3 = $80/month

**EBS Snapshot Lifecycle Manager (DLM)**:
- Automates creation, retention, and deletion of EBS snapshots
- Snapshots are incremental — only changed blocks cost money after the first snapshot
- DLM can tag snapshots and enforce retention windows (e.g., keep last 7 daily + 4 weekly + 12 monthly)
- Orphaned snapshots (the source volume was deleted) are a common source of waste — DLM helps prevent accumulation

**Delete on Termination**:
- EC2 root volumes have `DeleteOnTermination=true` by default — good
- Additional EBS volumes default to `DeleteOnTermination=false` — change this for ephemeral volumes to avoid orphaned volumes

**Unused volumes**: Detached EBS volumes still incur the full provisioned storage charge. AWS Trusted Advisor flags unattached volumes.

### EFS Cost Optimization

EFS Standard is ~$0.30/GB/month — significantly more expensive than S3. EFS Infrequent Access (IA) is $0.025/GB/month with a $0.01/GB retrieval fee.

EFS lifecycle management moves files that have not been accessed for a configurable period (1 day to 90 days) to the IA storage class automatically. Enabling this for a typical file share where 80% of files are accessed rarely can reduce EFS bills by 50–70%.

### S3 Requester Pays

When a bucket is configured with Requester Pays, the AWS account making the GET/PUT request is charged for data transfer costs, not the bucket owner. This is useful for distributing large public datasets (e.g., genomics datasets, satellite imagery) where the data owner does not want to absorb egress costs. Requesters must authenticate with AWS credentials — anonymous access is disabled in Requester Pays mode.

## Decision Flow

### Which S3 storage class?

```
Unknown or mixed access patterns?
  → Intelligent-Tiering (no retrieval fee risk)

Known access frequency:
  Accessed multiple times/month?
    → Standard
  Accessed <1x/month, needs ms retrieval?
    → Standard-IA (must tolerate 30-day minimum)
  Is the data re-creatable if AZ fails?
    → One Zone-IA (20% cheaper than Standard-IA)
  Archive that needs ms retrieval?
    → Glacier Instant Retrieval
  Archive with minutes/hours retrieval OK?
    → Glacier Flexible Retrieval
  Compliance archive, retrieval in hours?
    → Glacier Deep Archive (cheapest)
```

### gp2 or gp3 for EBS?

Always prefer gp3 for new volumes and migrate existing gp2 volumes. gp3 is cheaper and more flexible — there is no scenario where gp2 is preferable to gp3 unless a legacy application has a hard dependency on gp2 behavior.

## Hands-On

### Create an S3 Lifecycle Policy (CLI)

```bash
# Create a lifecycle configuration JSON file
cat > lifecycle.json << 'EOF'
{
  "Rules": [
    {
      "ID": "log-archival-rule",
      "Status": "Enabled",
      "Filter": { "Prefix": "logs/" },
      "Transitions": [
        { "Days": 30,  "StorageClass": "STANDARD_IA" },
        { "Days": 90,  "StorageClass": "GLACIER" },
        { "Days": 365, "StorageClass": "DEEP_ARCHIVE" }
      ],
      "Expiration": { "Days": 730 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}
EOF

# Apply lifecycle policy to a bucket
aws s3api put-bucket-lifecycle-configuration \
  --bucket my-app-logs-bucket \
  --lifecycle-configuration file://lifecycle.json

# Verify the policy was applied
aws s3api get-bucket-lifecycle-configuration \
  --bucket my-app-logs-bucket
```

### Enable S3 Intelligent-Tiering on a Bucket

```bash
# Enable Intelligent-Tiering configuration with Archive tier after 90 days
aws s3api put-bucket-intelligent-tiering-configuration \
  --bucket my-content-bucket \
  --id "FullTieringConfig" \
  --intelligent-tiering-configuration '{
    "Id": "FullTieringConfig",
    "Status": "Enabled",
    "Tierings": [
      { "Days": 90, "AccessTier": "ARCHIVE_INSTANT_ACCESS" },
      { "Days": 180, "AccessTier": "DEEP_ARCHIVE_ACCESS" }
    ]
  }'

# Check the configuration
aws s3api get-bucket-intelligent-tiering-configuration \
  --bucket my-content-bucket \
  --id "FullTieringConfig"
```

### Migrate gp2 EBS Volume to gp3

```bash
# List EBS volumes that are gp2
aws ec2 describe-volumes \
  --filters Name=volume-type,Values=gp2 \
  --query 'Volumes[*].{ID:VolumeId,Size:Size,IOPS:Iops,State:State}' \
  --output table

# Modify a volume from gp2 to gp3 (live, no downtime)
aws ec2 modify-volume \
  --volume-id vol-0123456789abcdef0 \
  --volume-type gp3 \
  --iops 3000 \
  --throughput 125

# Monitor the modification progress
aws ec2 describe-volumes-modifications \
  --volume-ids vol-0123456789abcdef0 \
  --query 'VolumesModifications[*].{State:ModificationState,Progress:Progress}'
```

### Create an EBS DLM Snapshot Policy

```bash
# Create an IAM role for DLM (if not already present)
aws iam create-role \
  --role-name AWSDataLifecycleManagerDefaultRole \
  --assume-role-policy-document '{
    "Version":"2012-10-17",
    "Statement":[{"Effect":"Allow","Principal":{"Service":"dlm.amazonaws.com"},"Action":"sts:AssumeRole"}]
  }'

aws iam attach-role-policy \
  --role-name AWSDataLifecycleManagerDefaultRole \
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSDataLifecycleManagerServiceRole

# Create a snapshot lifecycle policy
aws dlm create-lifecycle-policy \
  --description "Daily snapshots, 7-day retention" \
  --state ENABLED \
  --execution-role-arn arn:aws:iam::123456789012:role/AWSDataLifecycleManagerDefaultRole \
  --policy-details '{
    "PolicyType": "EBS_SNAPSHOT_MANAGEMENT",
    "ResourceTypes": ["VOLUME"],
    "TargetTags": [{"Key":"Backup","Value":"true"}],
    "Schedules": [{
      "Name": "Daily",
      "CreateRule": {"Interval": 24, "IntervalUnit": "HOURS", "Times": ["03:00"]},
      "RetainRule": {"Count": 7},
      "CopyTags": true
    }]
  }'
```

### Find and Alert on Unused EBS Volumes

```bash
# List all detached EBS volumes (you are paying for these but they are not in use)
aws ec2 describe-volumes \
  --filters Name=status,Values=available \
  --query 'Volumes[*].{ID:VolumeId,Size:Size,Type:VolumeType,Created:CreateTime}' \
  --output table

# Delete a specific unused volume (CAUTION: irreversible)
# aws ec2 delete-volume --volume-id vol-0123456789abcdef0
```

<ExamAngle>
## What the Exam Tests

- **Intelligent-Tiering vs Standard-IA for unknown patterns**: Intelligent-Tiering has no retrieval fee, making it safer when access patterns are unpredictable. Standard-IA charges per-GB retrieval, so it can cost more than Standard if data is accessed frequently.
- **Lifecycle transition direction**: Lifecycle policies can only transition objects to cheaper (colder) storage classes. You cannot create a lifecycle rule to move an object from Glacier back to Standard — you must use a Restore operation and then re-upload.
- **Minimum storage duration billing**: Storing an object for 10 days in Standard-IA and then deleting it still charges you for 30 days. The exam will present scenarios where this makes Standard cheaper for short-lived objects.
- **One Zone-IA risk**: 20% cheaper than Standard-IA but data is destroyed if that single AZ fails. Only appropriate for data that can be re-created or re-fetched from another source.
- **gp3 migration**: The exam increasingly expects you to recommend gp3 over gp2 for new and existing workloads. gp3 is always cheaper and has better baseline IOPS included.

## Common Traps

- **Forgetting multipart upload cleanup**: Large S3 buckets with frequent uploads accumulate failed multipart uploads. Without an `AbortIncompleteMultipartUpload` lifecycle rule, these invisible partial uploads continuously accrue storage charges.
- **Confusing Glacier Restore with Lifecycle**: A Lifecycle rule can move an object from Standard to Glacier, but once in Glacier, a Lifecycle rule cannot move it back. A temporary Restore makes a Standard copy available for a specified number of days, but the original stays in Glacier.
- **Deep Archive minimum duration**: Objects stored in Deep Archive are billed for a minimum of 180 days. Using Deep Archive for data that is deleted or transitioned before 180 days results in higher costs, not lower.
</ExamAngle>
